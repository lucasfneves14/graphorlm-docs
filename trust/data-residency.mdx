## The footprint

All Graphor production processing and storage occurs in the **`us-central1` Google Cloud region (Iowa, USA)**, with one exception: large-language-model inference is served from US AWS regions through Amazon Bedrock. There are no other production regions, no multi-region buckets, no edge caches that hold customer content, and no replication across continents.

This single-region posture is intentional. Regulated customers benefit from a residency story that fits on one line and that an auditor can verify with a single check per component.

## 1. Per-component residency

The table below covers every component of the Graphor production environment that touches customer data, including derived content and operational telemetry. Anything not listed here does not process customer data.

| Component | Service | Region | Notes |

| Ingestion / processing / post-processing workers | GKE (Google Kubernetes Engine) | `us-central1` | Three Temporal worker pools handle ingestion orchestration, document partitioning, and post-processing (chunking + embedding + indexing). |
| Data-processing service (GPU) | Cloud Run with NVIDIA L4 GPU | `us-central1` | Hosts the document-parsing pipeline (OCR, partitioning, visual embedding). |
| Model-serving microservices | Cloud Run | `us-central1` | In-house parsing models (Chandra, PaddleOCR VL) used by the data-processing service. |

## 2. AI model providers

AI inference is the only customer-data path that leaves Google Cloud. The provider chain (and the regions involved) is summarized below; full subprocessor characterization is in [Subprocessors](/trust/subprocessors).

| Provider | Production region(s) | Customer data sent | Retention |
|----------|---------------------|---------------------|-----------|
| **AWS Bedrock** (serves Anthropic Claude family) | **US regions only** — `us-east-1`, `us-east-2`, `us-west-1`, `us-west-2`. The São Paulo region (`sa-east-1`) is configured as an optional failover but is not active in standard routing. | Per-request: the user's question, retrieved chunks, conversation history, system prompt. | Per AWS Bedrock data-protection commitments — content is processed and encrypted in the AWS region selected; not retained for training; not shared with model providers. |
| **OpenAI** (embeddings + optional reranker) | Not pinned by basic documentation. | Per-build: chunk text for embedding. Per-request (only when reranker is enabled, which is off by default): retrieved chunks. | **Zero Data Retention enrolled** — abuse-monitoring logs eliminated. See [Model Use and Training §4.3](/trust/model-use-and-training#43-openai-llc--embeddings-and-optional-reranker). |
| **Cerebras** (chunk enrichment + fast-tier inference) | US-based infrastructure. | Per-build: chunk text for enrichment. Per fast-tier request: user question + retrieved chunks. | Zero retention per published Privacy Policy. |

No customer content transits any region that is not listed above.

## 3. International transfer regime

Synapse is incorporated in Brazil and the catalyzing pilot customers are subject to LGPD; the same posture also satisfies GDPR for European customers.

| Transfer leg | Legal basis | Source of contract |
|--------------|-------------|---------------------|
| Customer → Synapse | Direct controller-to-processor relationship under the Graphor [Data Processing Addendum](/legal/dpa-template). | Synapse–Customer DPA. |
| Synapse → Google Cloud (`us-central1`) | LGPD art. 33 + 35 (international transfer to a country with adequate protection or under contractual safeguards). Inherited via the Google Cloud DPA, which incorporates Standard Contractual Clauses 2021/914. | [Google Cloud Data Processing Addendum](https://cloud.google.com/terms/data-processing-addendum). |
| Synapse → AWS Bedrock (US regions) | LGPD art. 33 + 35; AWS DPA incorporates Standard Contractual Clauses. | [AWS Data Processing Addendum](https://aws.amazon.com/compliance/gdpr-center/). |
| Synapse → OpenAI | LGPD art. 33 + 35; OpenAI DPA incorporates Standard Contractual Clauses; ZDR addendum signed. | OpenAI DPA + ZDR addendum. |
| Synapse → Cerebras | LGPD art. 33 + 35; subject to Cerebras Terms of Use and Privacy Policy commitments cited in [Model Use and Training §4.4](/trust/model-use-and-training#44-cerebras-systems-inc--chunk-enrichment-and-fast-tier). | Cerebras Terms of Use + Privacy Policy. |
| Synapse → Neo4j AuraDB | LGPD art. 33 + 35; Neo4j AuraDB DPA incorporates Standard Contractual Clauses. | [Neo4j AuraDB DPA](https://neo4j.com/legal/data-protection-addendum/). |
| Synapse → Stripe | LGPD art. 33 + 35; Stripe DPA incorporates Standard Contractual Clauses. Stripe processes only billing identifiers, not Customer Content. | [Stripe DPA](https://stripe.com/legal/dpa). |

Every transfer is governed by a contract that incorporates Standard Contractual Clauses or an equivalent. The complete set of clauses is referenced and made available to enterprise customers under NDA via [privacy@graphorlm.com](mailto:privacy@graphorlm.com).

## 4. Why us-central1

A single GCP region was chosen rather than a multi-region GCS deployment or a cross-region active-active design for three reasons:

1. **Auditability.** A regulated customer can verify the residency claim by running a single command per component (`gcloud run services describe`, `gcloud sql instances describe`, `gsutil ls -L`, etc.) and confirming the region. A multi-region claim demands provider-level trust that data does not move between sub-regions.
2. **Predictable latency for the Brazilian user base.** `us-central1` (Iowa) is one of the lower-latency US regions for traffic originating in Brazil over public-internet routes. The latency tradeoff vs `southamerica-east1` (São Paulo) is acceptable for current traffic patterns; see [§5](#5-roadmap) for the Brazil-region roadmap.
3. **Subprocessor co-location with AWS US regions.** Bedrock-hosted inference returns to Graphor over public network paths; co-locating the Graphor backend with the Bedrock regions reduces round-trip variance.

The migration of the GCS datasets and models buckets from US multi-region to `us-central1` single-region was completed as part of this trust-documentation initiative. Stg is intentionally not migrated — it does not host real customer data.

## 5. Roadmap

Two alternative regions are on the roadmap. Neither has a committed delivery date — both unlock on customer request for the enterprise tier, subject to a cost/timeline review per customer.

**EU region (`europe-west1` or equivalent)** — for GDPR-bound customers that require EU-only residency end-to-end. Tradeoffs:

- Requires migrating GCP-native components (Cloud Run, Cloud SQL, GCS, GKE, Memorystore, BigQuery, Cloud Functions, Artifact Registry, KMS) to an EU region.
- Requires switching the Bedrock region to `eu-central-1` or `eu-west-3`. Anthropic Claude availability in EU Bedrock regions varies by model; the Standard tier model would be pinned to whichever Opus version is GA in the chosen EU Bedrock region at the time of provisioning.
- OpenAI does not pin a residency region today; the EU posture would rely on the OpenAI ZDR addendum (zero retention) as the compensating control, or replace OpenAI embeddings with a self-hosted embedding model on the EU GKE cluster.
- Neo4j AuraDB supports EU regions natively.

**Brazil region (`southamerica-east1`, São Paulo)** — for LGPD-bound customers that prefer Brazilian residency, or for customers in regulated sectors where Brazilian residency is explicitly required (some federal-government workloads, certain Bacen guidelines). Tradeoffs:

- GCP supports the full Graphor stack in `southamerica-east1`.
- AWS Bedrock is **already available in `sa-east-1`** (São Paulo) — Anthropic Claude on Bedrock is GA in this region as of 2025. The Standard tier could be served entirely from Brazilian regions if the customer requires it; this is the lightest-lift alternative residency option.
- Neo4j AuraDB does not currently offer a São Paulo region; the Brazil deployment would either accept a North-American AuraDB managed instance (with the contractual residency commitment from Neo4j) or migrate to a self-hosted Neo4j on the São Paulo GKE cluster.
- OpenAI embeddings remain non-region-pinned; same compensating control as the EU case.

Customers interested in either region should email [privacy@graphorlm.com](mailto:privacy@graphorlm.com) with a brief description of the residency requirement (regulatory citation, contractual obligation, internal policy). A scoping conversation establishes feasibility, timeline, and any incremental cost surcharge for the alternative region's infrastructure.

## 6. Things that explicitly do NOT happen

Stating these explicitly removes ambiguity for security and privacy reviewers:

- **No cross-region replication of Customer Content.** The GCS datasets bucket is single-region; the Postgres primary has no cross-region replica; backups stay within the GCP region's redundancy posture.
- **No CDN caching of authenticated responses.** Cloud Run responses to authenticated API calls are not cached in any edge location. Public marketing assets on `graphorlm-prd-public-assets` may be edge-cached but contain no Customer Content.
- **No content sent to a multi-region or global resource by default.** The legacy multi-region `US` datasets bucket has been migrated; no production component routes customer data through a multi-region resource.
- **No silent regional failover.** AWS Bedrock has configured failover regions (US-only) that activate on quota or availability events; the failover regions are all US. The configured São Paulo failover slot is currently disabled — a future activation will be published on the [Subprocessors](/trust/subprocessors) page before it takes effect.
